# Waterfall：问题定义、已有工作与最小评测方案

> 历史材料：保留当时内容，不作为现行方案。当前以 [研究主方案](../../01-研究主方案.md) 和 [输入输出与数据流](../../02-输入输出与数据流.md) 为准。

核验日期：2026-10-14。依据：用户指定的两段对话、`/Users/luoyige/Downloads/Waterfall_v1.pptx` 全部可提取文字，以及当前工作区的 S Agent 与排序源码。论文以原文、正式论文集、作者代码和官方数据说明为依据。这里是查新与实验设计，没有新增性能实验；文中的例子和样本规模均是示意或建议。

**结论先说：Agent 召回、Agent 排序、自然语言调整信息流、输出记忆操作，都已有直接相关工作。当前不能把它们分别认定为 Waterfall 的新算法贡献。** 最接近的工作已经覆盖跨平台行为、长期与当前需求、选源检索、推荐编排和反馈更新。Waterfall 可以继续研究，但需要一个具体可验证的改进，不能只靠“把这些环节接起来”。

**1．先把你现在做的事情说准确**

召回就是“去找备选内容”，排序就是“决定先看哪几条”。推荐是整个过程，不只是排序。跨平台历史、跨平台找内容、跨平台统一展示，是三个不同能力，不能互相替代。

| 环节 | PPT 与当前代码能支持的描述 | 目前不能直接声称 |
|---|---|---|
| 用户表达 | 对话解析优先主题的增加、删除 | 已完整理解并执行所有用途、硬性排除、时效条件 |
| S Agent | 结合行为与已有状态，强化/削弱兴趣，保持/替换/清空下一阶段搜索词 | Agent 已自主控制平台、分页、搜索比例或直接搜索 |
| 内容获取 | 程序在用户开启的来源中，按搜索词、轮转与库存规则拉取 | 每次选源和翻页都是模型判断 |
| 排序 | Agent 更新的兴趣参与程序评分；程序再去重、选批、交错来源 | LLM 逐条比较候选并输出最终排列 |
| 浏览 | 当前卡片与接下来窗口受保护，后台准备后续内容 | 用户表达后立即看到符合要求的内容 |

证据：PPT 第12、13、15、20、21、23页；[S Agent 提示词](../../../../../waterfall-anything/hive/waterfall/state/WaterfallSAgentPrompt.ets:1)、[输入和输出类型](../../../../../waterfall-anything/hive/waterfall/state/WaterfallSAgent.ets:5)、[排序入口](../../../../../waterfall-anything/hive/waterfall/core/aiphone/runtime/WaterfallAnythingCore.ets:704)。源码是本次静态读取结果，没有做真机行为验证。

更准确的当前定位是：**由 Agent 维护偏好和搜索计划的持续内容推荐系统。** Agent 间接改变排序也有价值；实验要测这种控制的收益，不需要为了名字强行加一个 LLM 排序器。

**2．哪些成熟，哪些是新近已有工作**

| 你的想法 | 直接相关的已有工作 | 创新判断与区别 |
|---|---|---|
| 点赞、点击、观看时间用于推断兴趣 | [MIND](https://msnews.github.io/)、[KuaiRand](https://kuairand.com/) 已定义行为和推荐任务 | 成熟基础；组织成 JSON 不是新方法 |
| 从多个独立来源寻找内容 | [ReSLLM](https://arxiv.org/abs/2401.17645) 用 LLM 做来源选择 | 多源检索与选源已有研究，不是平台只能推荐自家内容就没有前例 |
| 根据浏览历史，让 Agent 到不同网站检索并推荐 | [AgentWebBench](https://proceedings.mlr.press/v306/zhong26n.html)，ICML 2026 | 已包含网页推荐与多站点交互；是基准，不是一套已证明最优的方法 |
| 跨平台行为形成用户状态，再跨源寻找和编排内容 | [ClawRec](https://arxiv.org/html/2607.23779)，2026-07预印本 | **最接近整体构想**：时序用户状态、当前任务、选源、搜索、互补内容编排和反馈。不能把整个组合当首次；其主基准使用合成用户轨迹 |
| 自然语言“多看/少看”，转成操作调整下一屏 | [RecBot](https://arxiv.org/html/2509.21317v2)，[KDD 2026正式名单](https://kdd2026.kdd.org/papers/) | **最接近对话调推荐**：解析结构化要求，再调过滤、匹配、降分、合分工具。它也不是只能输出聊天文字 |
| 用指令和动态记忆重新排序 | [iAgent](https://aclanthology.org/2025.findings-acl.928/)，Findings ACL 2025 | 指令控制推荐、动态个性记忆已有直接前例；不能只与关键词排序比 |
| Agent 输出“强化/削弱/合并/遗忘记忆” | [MARS](https://arxiv.org/html/2605.14401v2)，2026-05预印本 | **最接近 S Agent 的操作形式**：事件、偏好、画像分层，规划离散记忆操作。操作名称或数量不同不足以构成新贡献 |
| LLM 生成主题，传统模块检索排序，异步缓存 | [CTV Content Discovery](https://arxiv.org/abs/2607.09988)，2026-07预印本 | 混合架构和延迟优化已有工程研究；其反馈闭环仍有局限，但不能因此忽略 ClawRec 等其他工作 |
| 用跨平台历史改善平台候选的排序 | [MediateRec / PAMO](https://arxiv.org/abs/2610.07588)，2026-10-06预印本 | 已研究个人 Agent 的重排，也衡量“改对了”和“把原来正确的改坏了”；跨平台历史不等于跨平台主动召回 |
| 长短期需求、自然语言控制及过期后的恢复 | [PersonaMem-v3](https://arxiv.org/abs/2608.21381)，2026-10-07更新预印本 | 已提供相关评测方向；真实行为作为种子、再合成扩展，不能冒充全程真实跨平台日志 |
| 延迟行为反馈用于更新 Agent 记忆 | [TIDE](https://arxiv.org/abs/2609.37544)，2026-09预印本 | 已处理反馈归因和记忆演化，但任务是营销内容生成；“有延迟反馈”本身也不是空白 |

上表中的预印本已有公开方法，查新时必须考虑；其发表状态与结论可靠性应和正式会议论文分开。表中是本次核验到的相近工作，不是对全球文献的穷尽证明。

**3．Agent 输出操作，新吗？**

**形式上不新。** 过去的方法可以输出一个分数、一串内容 ID，也可以输出工具和参数，让程序执行搜索、过滤、加减分或更新记忆。RecBot 与 MARS 已分别覆盖后两类。你的 `strengthen/weaken/similar` 属于“修改推荐状态的操作”。

例如用户说“相机已经买好了，想学夜景”：可以把下一轮查询改成“手机夜景教程”，但仍保留长期摄影兴趣。这里值得测的是**这次操作是否正确、何时执行、最终有没有改善内容**，而不是能否输出一个合法 JSON。

不宜预设每个案例只有一种正确操作。两种搜索词都可能带回好内容；合法性可以精确检查，决策质量主要看后续结果，同时抽样审核是否错误删除兴趣或违反用户要求。

**4．建议的问题定义与创新边界**

可直接用于讨论的总体问题：

> 在有限的模型与搜索调用预算下，如何把用户的明确要求和含糊浏览行为，转成持续有效的跨平台搜索与推荐调整，让用户少纠正、少等待，并持续看到有用的新内容？

**这是合理的问题定义，但已不是无人研究的新任务。** 当前材料尚未显示一个与最近工作明确不同、并有实验支持的方法创新。

更贴合 Waterfall 现有系统、值得先检验的窄问题是：

> 当用户需求已改变，但信息流仍混有旧计划拉取的内容时，Agent 能否判断一次反馈应该只改变下一轮搜索，还是也应改变长期兴趣，从而减少错误学习，并更快改善后续实际展示？

举例：用户长期喜欢摄影，刚说“今天先看足球”；接着刷过的是库存里的旧摄影内容。直接把这些跳过当作“不喜欢摄影”，会污染长期兴趣。可以比较保留反馈来路与时间、只看最近反馈、每轮重读历史三种方法。

这仍是**候选研究假设**，不能声称已查明空白。ClawRec 已有证据来路和任务过期，MARS 已有记忆操作，TIDE 已有延迟归因。Waterfall 必须进一步证明：在真实连续浏览、异步补货和固定预算条件下，某个明确决策机制比这些强方法稳定更好，或用更少调用达到同等质量。

对应三个可被证伪的问题：

| 问题 | 最少要观察什么 | 什么结果会否定优势 |
|---|---|---|
| 召回是否改善 | 同源、同模型、同预算下，新找到的有用且不重复内容 | 只比一次规划好，却不如普通多轮 Agent |
| 推荐是否改善 | 同候选下，Agent 更新兴趣后，前几条是否更合适 | 只是候选变好了，固定候选排序没有收益 |
| 持续更新是否值得 | 需求改变后适应速度、旧兴趣误改率、恢复效果、总成本 | 只在合成案例有效，或多十倍调用换来很小改善 |

若最终贡献主要是低延迟、可控、真实跨源闭环，那么应诚实作为系统方法与实证贡献来组织。9/9/2、Top10、80/20/5 等工程参数本身不构成算法创新。

**5．公开数据与现在的输入，哪些相同**

你当前 S Agent 已有结构化输入：时间、行为类型、内容 ID、标题/摘要、来源、检索词、`durationMs`、程序计算的 `heat` 和 `planRevision`。无需重新发明一套“行为数据”。需要的是保留数据含义的适配。

| 行为 | 公开数据中的真实定义 | 与 Waterfall 的关系 |
|---|---|---|
| 点赞 | KuaiRand `is_like` | 可作为相近的显式正反馈；0通常只是没有点赞 |
| 点击/打开 | MIND 候选后缀 `-1/-0`；KuaiRand `is_click` 随展示形态可表示点击或有效播放 | MIND点击不能直接变成 Waterfall“打开且停留超过1秒”，因为缺时间 |
| 视频播放 | KuaiRand `play_time_ms`、`duration_ms`；KuaiRec `play_duration`、`video_duration`、`watch_ratio` | 不等于 Waterfall B站卡片的前台可见停留；重复播放时比例可以超过1 |
| 文章阅读 | [EB-NeRD](https://recsys.eb.dk/dataset/) 提供阅读时间与滚动比例 | 比视频时长更贴近文章，但仍应保留各自计时方式 |
| 刷过 | MIND曝光未点，只能知道未点击 | 不能证明真实滑过，更不能自动标为讨厌 |
| 取消赞 | Waterfall `unlike` 是撤回点赞 | 不能映射成 KuaiRand `is_hate` 的显式负反馈 |
| 修改要求 | Waterfall `p_changed`；PersonaMem-v3有语言控制评测 | MIND、KuaiRand没有等价的原生自然语言要求 |
| 搜索来路 | Waterfall `keywords` 来自真实搜索词 | 数据集 category/tag不能填进去冒充搜索证据 |

当前 Waterfall 特有阈值：`open > 1000ms`；B站可见停留3秒起为弱信号、15秒起为较强信号。提示词明确说明这不是播放器确认的观看时间。`heat` 的 5/3/1 是程序赋值，不是数据集真值。当前 S Inbox没有接收所有 UI 行为，不能把收藏、分享等自动算进现有 Agent 输入。[记录逻辑](../../../../../waterfall-anything/hive/waterfall/state/WaterfallSAgent.ets:204)

推荐保留的共同结构，用人话就是：**谁、什么时候、在哪个平台、对哪条内容、做了什么、测了多久，以及这条内容为什么被推荐出来。** 额外标明时长是“播放”“页面活跃”还是“卡片可见”，缺数据写缺失，不能补0。原始事件与“推测用户喜欢什么”分开保存。

还有一个直接影响实验的限制：当前 `planRevision` 在记录行为时取当时的 S 状态版本，不能证明内容最初由这个版本搜来。研究旧计划归因时，必须另外追踪原始查询、获取时的计划版本、取回/展示/反馈时间；本次未修改埋点。

**6．数据从哪里来，先用哪些**

| 数据 | 一条样本的人话例子 | 最合适用途 | 不足与优先级 |
|---|---|---|---|
| [MIND](https://msnews.github.io/) | 以前看过A、B；这次显示C、D、E，点了D | 同候选新闻排序 | 无点赞/停留；全库召回需另定协议。首轮可用small；本次未重测下载权限 |
| [KuaiRand-1K](https://kuairand.com/) | 某时看了视频X，播放36秒并点赞 | 行为输入、按时间更新画像 | 选1K/27K；Pure裁掉大量历史，不适合证明连续学习。语义caption/category补充需另行联接核验 |
| [KuaiRec](https://kuairec.com/) | 对相对完整的一批视频记录看多久 | 视频排序辅助验证 | 主要是观看比例，没有逐交互原生点赞；不必首轮全跑 |
| [BEIR](https://github.com/beir-cellar/beir) | 查询“某科学论断”，哪些论文相关 | 搜索组件和查询改写 | 无完整用户兴趣，不代表跨平台推荐 |
| [AgentWebBench](https://github.com/cxcscmu/AgentWebBench) | 给浏览历史，通过多个网站接口找下一批网页 | 多源召回能力 | 很贴近召回；网页推荐标签稀疏，不能单靠一个分数判断实际有用性 |
| [ClawRec-SimBench](https://github.com/wuchenghao0215/ClawRec) | 跨平台行为轨迹，对当前生活任务推荐下一步内容 | 最近方法的直接对照 | 用户轨迹主要是合成；能借协议，不等于真实用户实验 |
| [PersonaMem-v3](https://arxiv.org/abs/2608.21381) | 过去喜欢A，本周临时多看B，过期后恢复 | 混合行为、语言控制、需求时效 | 真实行为种子加合成扩展；适合补测，不替代真实信息流 |
| [EB-NeRD](https://recsys.eb.dk/dataset/) | 新闻曝光、点击、阅读时间、滚动比例 | 需要文章停留时扩展MIND | 丹麦文，需注意语言与阅读计时差异 |

建议的最小组合：**跨源召回参考 AgentWebBench 的环境与对照，排序用 MIND-small，行为输入用 KuaiRand-1K；主要的实际有用性证据补小型跨平台需求变化测试。** AgentWebBench的稀疏下一网页标签只作补充，不能独自承担主要体验结论。PersonaMem-v3/ClawRec-SimBench先查接口、跑少量开发样例，用来检查是否遗漏最近工作已覆盖的能力。无需一开始把所有数据跑一遍。

公开数据给“内容、过去行为、部分评分依据”，不必拿来训练新模型。你可以固定现有模型，在Mac上做小样本推理和评分。不要把另一个数据集里相同数字ID当作同一个用户；也不要把KuaiRand标签直接套到B站内容上。

**7．召回怎么比：有没有找到该找的内容**

受控版本：准备一个冻结内容库和独立标注。例如库里有1,000条内容，其中10条适合“手机夜景教程、不要器材广告”。每种方法最多带回100条。A找回4条，B找回7条，那么 Recall@100 分别是40%和70%。**分母是已知相关内容，不是带回的100条。** 这是说明用例，不是Waterfall结果。

公平对照保留四组：①最近兴趣关键词；②同一个大模型一次生成查询；③同模型能看结果并继续改查询的普通搜索Agent；④Waterfall。选择来源权限、搜索引擎、模型、可见历史、调用预算、去重方法保持一致。增加 ClawRec 或其有明确标注的复现，检验最近方法；改了原论文流程要写“adapted”，不能冒充原结果。

真实跨平台版本：例如同样最多10次搜索，比谁找到的**有用且不重复**内容更多、前10条有用比例更高、成本更少。把各组返回并集去重后交给不知道方法身份的评审，按同一用户需求评分，冻结内容快照。全网相关内容总数不知道，所以不能声称“全网召回率70%”。如果用并集作分母，只能称“已标注池内的召回”，且说明漏标限制。

只和BM25这种按词匹配方法比较，不足以证明你的Agent策略有新优势；给Waterfall更多请求或更多用户信息也不是公平比较。

**8．推荐排序怎么比：同一批内容，谁把好内容放前面**

给各方法同一批20条内容和同一份用户资料，隐藏以后点击/点赞的答案，只让它们改变顺序。对照：原排序、历史相似度、同一LLM直接排序、iAgent/MARS类更新记忆再排序、Waterfall当前机制。现有训练型推荐模型可作为额外质量参照，但需单列训练数据/预算；首轮无需自己训练大模型。

| 指标 | 人话与例子 |
|---|---|
| Precision@10 | 前10条有7条有用，就是70%。这里的“有用”必须预先定义 |
| nDCG@10 | 好内容越靠前越高，通常0到1。不是准确率；候选和标签不同的两个数据集不能直接比数值 |
| 错误调整率/约束违规率 | 把原来合适的降下去，或仍展示明确禁止内容，是否减少；与有效内容数量一起看，防止靠全不展示“零违规” |

极小算例：三条内容，只有“教程A、教程B”有用。排序 `[A,B,广告]` 的 nDCG@3=1；`[广告,A,B]` 约为0.693。两者找到的内容完全相同，前3条有用比例也同为2/3，但后一种让用户先看广告，所以排序分更低。

MIND可用实际点击作替代标签，但“未点”不等于不满意。你要证明“符合明确要求”，应另做0=无用/违约、1=部分有用、2=很有用的盲评，并单独记录硬约束。训练/开发阶段确定规则，不能看了结果再改“有用”的定义。

**9．连续推荐怎么评：反馈以后，用户是否真的受益**

自建小型任务应记录：长期偏好、现在的需求、需求变化时间、可访问来源、各次搜索返回快照、展示顺序、真实反馈、独立评分和成本。先覆盖稳定兴趣、切换需求、临时需求结束、明确排除四类。50–100个开发决策点只用于发现流程问题，正式样本量依据先导波动确定，测试用户与开发用户分离。

例如“相机已买好，接下来学拍摄”：预先规定20条展示内至少出现3条合适教程，并报告后续10条的整体质量。若A刷8条才满足、B刷3条，B适应更快；超时任务仍算失败，不能从平均里删掉。同时记录从反馈到新内容实际显示的秒数；“偏好保存成功”不等于“已经看到”。

要分别观察新需求生效与临时需求结束后的恢复。P删除在当前产品里只是取消优先，不能把仍看到该主题判为违规；`unlike`同样不能按显式禁推评分。

**历史回放的底线：日志里用户看了A后点B，不能让新系统展示C，再把点B当成对C的反馈。** 静态日志适合测预测和受控更新；完整闭环需要实际用户反馈或明确标注的模拟环境。模拟用户与LLM评审可做开发，但不能让同一模型同时造用户、造答案、评自己后宣称真实满意度提升。

**10．怎样证明收益来自哪里**

先拆成四组：普通召回＋普通排序、Waterfall召回＋普通排序、普通召回＋Waterfall排序、完整Waterfall。单测排序必须同候选，测整个系统允许各自找出不同候选，但外部来源与预算一致。再只对最有希望的机制做关闭对照，例如记忆固定/更新、搜索计划固定/更新、是否保留真实来路。

每组都报告内容质量、失败/空结果、请求数、模型费用与等待。按用户或任务算差异和不确定范围；同一个用户100次操作不等于100个独立用户。把旧内容去重、相近内容重复、源故障等困难情况保留。

不要把公开排行榜分数当及格线。**好推荐是相同条件下，对这个人的当前目标更有用，且改善值得其成本。** 若更复杂的Agent在相同预算下没有赢，简化系统也是有效研究发现。

**11．需要纠正的旧表述**

- 之前把“Agent召回”和“Agent排序”直接叫两个创新，证据不足，应改为两个待验证环节。
- “用户只能点赞、不能用语言调信息流”不能再泛指已有研究，RecBot等已经明确做了这件事。
- “跨平台历史＋长期/短期偏好＋主动检索”不能当作尚无前例，ClawRec等高度相近。
- 你现有输入与公开行为日志相近，但可见停留、播放、未点击、取消赞的语义不能混同。
- 原对话中的BEIR/KuaiRand先导属于组件/数据检查，不能证明完整Agent胜出；本次没有重跑，也不把旧分数作为当前效果。
