**结论：获取、推荐、更新、回复与保持已覆盖核心能力。还需明确五件事：哪些信息可见、怎样结束会话、输出怎样执行、什么时候算观察完、不同系统怎样公平比较。**

## 2. 五个必要补充（Waterfall 设计建议）

| 缺口 | 最小补充 | 放在哪里 |
|---|---|---|
| **可见信息与研究答案的边界** | `run_meta` 保存系统条件、模型/提示词/工具版本、内容环境版本、随机种子（使用时）；`evaluation_private` 保存模拟用户隐藏设定、参考目标、事后评分和盲选答案 | 研究归档。Agent 输入仍只有当时开放且已收到的信息；工具说明及执行所需限制可见 |
| **会话起止与状态结果** | 保存 `started_at, ended_at, termination_reason` 以及 `initial_snapshot, final_snapshot`；原因区分用户离开、试验时限、系统错误等 | 会话归档/运行器。任务完成仅更新 task，不自动宣告整次会话成功 |
| **从模型文字到真实执行** | 每次保存 `raw_output, parsed_output, validation_errors, execution_results`；检查动作格式、引用 ID、来源能力、状态版本、依赖与重复 action_id | 执行器及轨迹。校验未通过的动作不执行，返回错误；已成功动作保留 |
| **曝光与未回应如何结束观察** | 每次真实曝光关联 `observation_end_at` 和 `observation_status=complete/interrupted`；日志未关闭时保持 pending | 客户端事件与归档。完整观察内没点击才能记“未点击”；未曝光或记录中断记未知，均不自动变为不喜欢 |
| **比较条件是否一致** | `comparison_id` 关联共同起点和可查询内容环境，记录真人条件分配/展示顺序；各系统后续分别保存自己的曝光、反馈和状态 | 研究归档。比较完整搜推时共享查询机会，允许不同系统实际取得不同候选 |

这些字段主要属于归档和运行器，不必全部塞进模型提示词。现有 `available_at`、`user_state.version`、action_id 和执行回执已经提供了基础。

### 输出解析与执行采用的最小规则

1. 保存模型原始回答，解析并校验 JSON；解析失败也保留为一次真实失败。
2. 将合法动作按依赖交给工具；同一 action_id 不重复提交。状态更新按现有 base_version 校验。
3. 保存每个动作实际返回及提交后的状态。只将实际返回的内容加入候选；推荐成功入队后，等待客户端记录实际可见。
4. 成功、失败及用户新反馈都进入下一次允许观察的输入；不把整段未来轨迹一次性给 Agent。

这里借鉴 τ²-bench 对执行结果和最终状态的分离；具体校验字段与动作规则是 Waterfall 的设计，不是该基准原有字段。

## 3. 一条完整归档应能读出什么

`run_meta + initial_snapshot → 每步(input, raw_output, parsed_output, validation, execution_results) → exposures/feedback_windows → session_end + final_snapshot → evaluation_private`

冷启动的 initial_snapshot 可以没有对话、行为和记忆；内容来源与工具能力仍需存在。终止记录由运行器或客户端产生，不能由 Agent 自报“任务完成”代替实际用户结果。结束后尚未返回的动作也应有最终回执或明确未完成状态。

## 4. 评价只增加必要的三层

- **执行是否成立：**合法动作是否成功、推荐 ID 是否真实存在、实际展示与记录是否一致。
- **用户体验与任务效果：**独立用户评分/盲选、是否得到有用内容、需求变化后是否跟上；有目标与随便刷分别定义成功。
- **整段过程：**从相同起点比较连续体验。各系统消费自己的反馈；不把不同系统每轮的赢家拼成一条轨迹。

τ²-bench 的启发是“结果正确可以有多条路径”；Waterfall 据此允许不同查询、来源和动作顺序。搜到某个指定 ID、与参考 JSON 完全一致、Agent 自报满意度，都不能单独代表用户体验成功。

Open Bandit 的启发是保存真实选择机制。未知概率记空，模型的置信度不能冒充 action_prob；确定性日志也不能仅靠补一个概率字段，就用于评价任意新策略的整段交互。当前优先采用真人随机条件/盲选与分条件连续使用，离线反事实估计留给具备相应采集条件的数据。

本轮核查第一方说明与代码，未运行这些基准、采集真人数据或修改产品；以上新增字段与规则仍需在采集实现中落实。

## 5. 核心评测：下一条内容盲选，与连续使用分别评价

**我们定义的好系统：在同一段经历之后，更常给出用户此刻最想看的内容；实际持续使用时也有帮助，并能跟随新的表达与行为。** 单步偏好与连续体验分别测量。以下协议是 Waterfall 的设计建议。

| 参考 | 原数据、标签与指标实际表示什么 |
|---|---|
| MIND | 原数据以曝光关联此前历史与本次点击/未点击。官方按每个 impression 分别计算 AUC、MRR、nDCG@5/10，再平均。AUC 比较点击项与未点击项的排序；官方 MRR 对所有点击项的倒数排名求平均，不能一概解释成“首个相关项的倒数”；nDCG 衡量点击项是否排得靠前。[数据格式](https://github.com/msnews/msnews.github.io/blob/master/assets/doc/introduction.md#behaviorstsv)、[官方评分代码](https://github.com/msnews/MIND/blob/master/evaluate.py) |
| KuaiRand | 日志含普通/随机曝光、时序、用户/视频特征及点击、赞踩、观看时长等多信号，可支持去偏、序列、多任务或交互推荐。采用 AUC、观看时长误差还是 NDCG，取决于具体目标、标签与候选设定，不强加一个固定“官方总分”。[资源论文](https://arxiv.org/abs/2208.08696)、[官方字段](https://kuairand.com/) |
| RecBot | 离线以历史中最后一次交互的 item 作留出目标；Recall/NDCG 看目标的召回和位置，PR 看有限轮内是否进入 top-5，CSR 看与目标属性的符合程度。它衡量的是该离线目标，不能直接解释成真人最想看哪条。[实验 §4.1](https://arxiv.org/html/2509.21317v2#S4.SS1) |
| ClawRec | 留出下一行为，以对该任务的支持度给内容打 1–5 分；所有方法 top-K 合为匿名评价池，IDCG 从该共享池计算。NDCG@20 看排序，Hit@20 看是否至少一项评分≥3。开发集用真人评分校准，测试集语义评分使用冻结后的 LLM judge。[评价 §4.1.2](https://arxiv.org/html/2607.23779v1#S4.SS1.SSS2) |

**最小可执行协议：**

1. **固定前缀。** 保存同一份已发生的原始历史和用户声明，各系统自行构建内部状态，使用相同来源能力和可查询内容环境，各给一条下一内容。允许搜索得到不同内容；所有结果生成完再展示。
2. **盲选。** 隐藏算法名称，统一卡片展示、随机左右顺序；保留正常可见的标题、内容来源和类型。用户选“最想看”“并列最好”或“都不想看”。同一内容合成一张卡，保留它对应的所有系统，得到同一判断；内容未产出也保留为失败记录。
3. **量化。** 对系统 i，`被选中率 = 其内容进入用户最佳集合的次数 / 分配给它的全部比较次数`；并列最佳和同内容的多个系统均记入，故各方法比率之和可以超过 1。全拒绝率按整组比较记录，不能冒充某一方法的单独拒绝率。固定参评系统数量/名单，并报告重复率；不同对手集合下的选择率不直接横比。按用户汇总，区间估计按用户重采样。
4. **需要跨系统集合比较时，做均衡两两盲选。** 记录 A胜/B胜/同样想看/都不想看；偏好胜率为 `(胜+0.5×同样想看)/(胜+负+同样想看)`，全拒绝另报，不能隐藏分母。多路盲选中两条都未被选中的内容，没有获得相互胜负标签。只有一张去重内容时改问“想看/不想看”，不制造假竞争。
5. **连续使用另测。** 会话级随机分配系统或平衡体验顺序，每个系统只接收自己展示后的真实反馈；结束时评“这段内容是否有用/值得看”，有明确目标时再评是否帮助完成。单步盲选不证明长期收益，也不把每轮胜者拼成一条假想算法轨迹；没有产出或提前中断的分配不悄悄剔除。

**NDCG@3 手算（二元标签）：**公式 `DCG@3 = Σ(2^rel_i−1)/log2(i+1)`，再除以同一评价候选范围内的理想 DCG；公式与上面 MIND 官方代码一致。
当前顺序 `[0,1,1]`：`DCG = 0 + 1/log2(3) + 1/log2(4) = 1.13092975`。
理想顺序 `[1,1,0]`：`IDCG = 1/log2(2) + 1/log2(3) + 0 = 1.63092975`。
因此 `NDCG@3 = 1.13092975 / 1.63092975 = 0.69342640`；相关项越靠前越好，理想顺序为 1。这是演算例子，不是 Waterfall 结果。
“相关”的含义由标签决定：MIND 是已记录的点击；ClawRec 是任务支持度；Waterfall 主盲选得到的是相对偏好。只选一条不等于其他条都无用，不能直接把未选内容全标 0 后声称得到可靠 NDCG。

若增加排序指标，可汇总各系统返回内容、去重、逐项匿名标注，再按各系统顺序计算，共用同一 IDCG。TREC 的 pooling 就是从多系统返回中建立待标注池；NIST 也研究了不完整标注可能带来的偏差。未标注的新内容先补标，不能自动判为无关。[NIST 对 pooling 及其局限的原始研究](https://www.nist.gov/publications/bias-and-limits-pooling-large-collections)
盲选最少归档 `prefix_id, comparison_id, method_ids, content_snapshot_ids, method_to_content, display_order, selected_content_ids, none_selected, judge_id, judge_type`；模拟用户另保存版本。选择题评“此刻想看”，连续试用评“看过后是否有用”，两者共同回答系统好坏。
