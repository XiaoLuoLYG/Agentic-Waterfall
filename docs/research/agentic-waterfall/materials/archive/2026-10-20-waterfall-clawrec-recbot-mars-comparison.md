# Waterfall 与 ClawRec、RecBot、MARS：写论文前的对照

> 历史材料：保留当时内容，不作为现行方案。当前以 [研究主方案](../../01-研究主方案.md) 和 [输入输出与数据流](../../02-输入输出与数据流.md) 为准。

核验：2026-10-20。三篇以论文原文为准；Waterfall 结合此前 PPT、指定对话和本次源码静态核验。例子是解释方法的示意，不是复现实验结果。

**结论：ClawRec 最接近整体构想，RecBot 最接近“用话改推荐”，MARS 最接近 S Agent 的记忆操作。Agent 召回、Agent 排序、输出操作、长短期兴趣分离，都不能单独作为新贡献。**

召回＝找来备选内容；排序＝决定哪些先看。

| 系统 | 输入后具体做什么 | 内容怎么找、怎么排 | 与 Waterfall 相同 / 关键差异 |
|---|---|---|---|
| [ClawRec](https://arxiv.org/html/2607.23779v1)，本次核对预印本 | 读跨平台行为、对话和反馈，维护当前任务、持久偏好及其证据；通过增量修改更新状态，处理过期与负反馈 | 按任务选择来源和查询；逐条评估用途、时效和约束，再挑一组互补、少重复的内容 | **整体重合最高**：画像→检索→编排→反馈已完整覆盖。其任务/证据/来源角色更明确；主评测是合成轨迹，不能直接证明真实连续刷流体验 |
| [RecBot](https://arxiv.org/html/2509.21317v2)；[正式论文 DOI](https://doi.org/10.1145/3770855.3817619) | 读用户指令、上一屏和历史偏好，拆成“想要/不要”“必须/尽量”，再规划工具操作 | 在已有平台候选池中调用过滤、匹配、负向降分和分数合并，生成下一屏；包含训练模型与蒸馏部署 | **相同**：自然语言改推荐，Agent 输出操作、程序执行。**不同**：论文重点是平台内候选重排，不是开放多源发现；你的现有 S Agent 也没有完整等价的硬约束过滤能力 |
| [MARS](https://arxiv.org/html/2605.14401v2)，本次核对预印本 | 从行为事件提炼偏好，再汇总画像；Agent 决定提取、强化、削弱、合并、遗忘、重写或跳过 | 把画像、最近行为、当前指令和候选交给 LLM 打分，按分数排序；实验主要在每次 10 个给定候选中选 | **相同**：记忆更新操作及按需更新。**不同**：它直接用 LLM 给候选打分；你的 S Agent 改兴趣与搜索词，最终顺序由程序评分、去重和混排决定 |
| Waterfall，当前读取的实现 | 从点赞、打开、部分来源的可见停留等行为，输出兴趣“强化/削弱”和下一阶段搜索词“保持/替换/清空”；用户明确主题另由对话工具修改 | 程序按已开启来源取内容，再结合兴趣、当前需求、新鲜度等评分、去重、混排；后台补货，保留当前及临近浏览窗口 | **具体特色**是持续多源信息流及其执行限制。当前还不能据此声称算法领先；S Agent 不直接选平台、翻页或输出最终列表，搜索词变化主要影响后续补货 |

Waterfall 的源码依据：[S Agent 提示词](../../../../../waterfall-anything-release/entry/src/main/hive/waterfall/state/WaterfallSAgentPrompt.ets:1)、[排序入口](../../../../../waterfall-anything-release/entry/src/main/hive/waterfall/core/aiphone/runtime/WaterfallAnythingCore.ets:704)。三份工作区中的 S Agent 提示词本次哈希一致；没有据此推断所有分支完全一致。

**用同一句话理解区别：**“相机买好了，现在想学夜景摄影。”

- ClawRec：结束购机任务，按新任务找教程等不同用途的内容，并组合推荐。
- RecBot：把“少看购买建议、多看教程”转成候选过滤和调分操作。
- MARS：更新相关偏好/画像，并用当前要求给已有候选重新打分。
- Waterfall：可以调整优先主题和下一轮搜索词；但旧库存仍可能继续出现，不能把“已改搜索词”当成“下一条已符合要求”。

前面三项是按论文机制解释的示意，不保证作者系统在这个具体案例中必然成功。

**建议保留两个候选研究方向，而不是四个宽泛创新点：**

1. **优先：指令变了，怎样让正在运行的信息流正确跟上？** 例如“今天只看足球，明天恢复摄影”，但旧摄影搜索还在返回、旧库存还在显示，用户又继续点赞/跳过。研究应同时处理指令的作用范围、在途结果、库存和反馈归因。现有三篇已处理任务变化或记忆更新，但本次未见专门验证这一整套异步场景。要比较的是：相同预算下，几条/多久开始符合新要求，误改多少长期兴趣，付出多少搜索和模型调用。仅加版本号、清空缓存或提示词提醒，不足以支撑方法创新。

2. **备选，难度更高：避免 Agent 被自己推出来的内容“带偏”。** 例如先猜用户爱摄影，于是连续推摄影，再把几次点击当作更强证据，越推越单一。可研究如何结合“用户究竟有机会看到什么”、行为可靠性和明确纠正，更新语言形式的偏好记忆。曝光偏差和反馈循环本身已有 [CIRS](https://arxiv.org/abs/2204.01266) 等研究；必须提出针对 Agent 记忆更新的具体新机制，不能把“去偏”重新命名。

适合先写下的问题定义：

> 当用户用自然语言改变当前需求时，如何在结果延迟到达、内容持续补充的多源信息流中，让指令快速且准确生效，并避免错误改写长期偏好？

这是**值得验证的研究问题，不是已经确认的新颖性结论**。若投 ACL，建议把主线放在指令语义、作用范围与状态更新的正确性；仅优化缓存和排序延迟更偏推荐/系统研究。可以先写问题与相关工作，贡献和结论应等方法与证据齐备后确定。
