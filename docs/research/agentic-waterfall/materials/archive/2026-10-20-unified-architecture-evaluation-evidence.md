# Waterfall 统一架构：数据与评估证据

> 历史材料：保留当时内容，不作为现行方案。当前以 [研究主方案](../../01-研究主方案.md) 和 [输入输出与数据流](../../02-输入输出与数据流.md) 为准。

核查日期：2026-10-20。本文是研究方案，不含实验结果；以下“建议”均未实施。

**建议最少采用：ClawRec-SimBench 做整条链路的离线主测，KuaiRand-1K 补真实行为序列，再自建一小组多轮需求变化场景。** 三者分别回答“能不能找对、排好”“面对真实反馈是否仍有效”“用户改变主意后是否及时调整”。不要把几个独立数据集上的分数相加，称作统一架构收益。

## 1. 哪些现成数据真正能覆盖全流程

| 数据 | 已核实能测什么 | 关键缺口与取舍 |
| --- | --- | --- |
| **ClawRec-SimBench** | 从历史推断需求，跨来源找内容，再输出有序推荐；事件间可保留记忆 | **适合作离线主测。** 用户意图轨迹是合成的，真实网页上的操作不等于真人需求；没有“系统推荐新内容后，真人如何反应”的真值 |
| **AgentWebBench** | 在多网站环境中，从浏览历史预测下一网页；可同时考验选网站、检索与排序 | 适合作外部迁移检查；推荐子集仅 281 例，论文报告接近零分且任务存在歧义，不能单独支撑连续个性化效果 |
| **KuaiSAR** | 同一平台真实搜索、推荐及二者切换 | `keyword`、`caption` 的词被散列成整数；不适合直接考语言 Agent 是否读懂原始搜索需求 |
| **KuaiRand-1K** | 真实有序视频反馈：点赞、显式负反馈、播放时长等；部分随机曝光 | 最合适的行为补充。没有自然语言临时目标、跨网站搜索，或任意新推荐的用户反应 |
| **KuaiRec** | 小矩阵近乎完整的用户×视频观看反馈 | 可做静态偏好查表环境；不能证明同一人在新时间、新顺序下仍给同样反馈 |
| **InstructRec（iAgent 配套）** | 结合指令与历史，从候选中推荐 | 指令由评论合成；论文评价使用 1 个目标加 9 个随机负例，不能当全库召回或真实多轮调整 |
| **MIND** | 带标题、摘要的新闻曝光与点击排序 | 没有点赞、停留或自然语言纠正；对本轮统一架构不是必加项 |
| **BEIR** | 给定需求，从固定文档库找相关文档 | 没有个性化历史与持续反馈；适合检索诊断，不足以评价完整 Waterfall |

主要来源：[ClawRec 论文 §3–4](https://arxiv.org/html/2607.23779v1)、[官方复现说明](https://raw.githubusercontent.com/RUCAIBox/ClawRec/main/docs/reproduction.md)、[AgentWebBench 论文 §3 与附录 H](https://arxiv.org/html/2604.10938v1)、[KuaiSAR 字典](https://kuaisar.github.io/detailed_statistics.html)、[KuaiRand 官网](https://kuairand.com/)、[KuaiRec 官网](https://kuairec.com/)、[iAgent 论文](https://aclanthology.org/2025.findings-acl.928.pdf)、[MIND 字典](https://learn.microsoft.com/en-us/azure/open-datasets/dataset-microsoft-news)、[BEIR 格式](https://github.com/beir-cellar/beir/wiki/Load-your-custom-dataset)。

几个容易选错的地方：

- **SimBench 的考试仍是“藏住下一步”。** 共 109 个模拟用户、545 个生活事件；20 个用户开发、89 个测试。每个事件在最后一步之前评测，系统能看以前事件和当前前缀，不能看隐藏目标。它能验证跨事件状态使用，但不能把测试中的下一条固定行为当成 Waterfall 推荐造成的反馈。[论文 §3.1–3.2](https://arxiv.org/html/2607.23779v1)
- **KuaiRand 用 1K，别默认 Pure。** Pure 只保留随机候选池视频相关日志，用户中间看过其他视频的过程被删掉；1K 保留抽样用户的发布历史。文本字幕已有补充，但要先检查所选版本的关联覆盖率；随机插入只占一小部分，整个数据不是随机实验。[官方版本与补充说明](https://kuairand.com/)
- **KuaiSAR 的整数不能“翻译回”原话。** 可读类别能支持较粗的内容理解；若另外生成标题或搜索句子，应明确称作合成改造。推荐时间是分发时间，批次可相同；搜索未点击也可能来自自动播放满足需求，不能直接当讨厌。[官方说明](https://kuaisar.github.io/detailed_statistics.html)
- **InstructRec 有同名工作。** 此处指 iAgent 的配套数据；不是把 2023 年《Recommendation as Instruction Following》的方法名当作同一数据集。[iAgent 官方仓库](https://github.com/WujiangXu/iAgent)、[2023 年论文](https://arxiv.org/abs/2305.07001)

## 2. 三层实验：每层回答一个问题

### 第一层：完整系统究竟有没有帮助

**建议：以 SimBench 为主，让每个系统从相同历史出发，自行找候选并排序，评价最终推荐。** 这时不能强制各系统拿完全相同的候选，否则会抹掉召回的作用。只有单测排序时，才固定候选。

保留官方用户划分，隐藏目标及其描述不得进入 Agent；事件按顺序运行，同一用户保留记忆，换用户清空。官方发布区分可见输入和 `private` 目标，复现时应保留这条边界。[官方复现说明](https://raw.githubusercontent.com/RUCAIBox/ClawRec/main/docs/reproduction.md)

建议统一模型、历史、工具权限、内容来源、搜索次数上限、Token/耗时预算、展示条数。跨网页运行需保存来源与返回快照；无法冻结网页时，在相近时间交错运行并报告失效页面比例。相关性评审应隐藏方法名称，固定评分规则，合并各方法结果去重后统一标注，并抽样请人核查。报告“在这些已评内容中更有用”，不能声称知道全网所有相关内容。

AgentWebBench 可选作一次外部验证，优先级低于把主测做扎实。其官方中央检索基线和分网站工具基线有不同访问条件；若要证明编排更好，必须统一可访问语料，或把全局访问基线另列为资源条件更强的参照。[官方代码与数据说明](https://github.com/cxcscmu/AgentWebBench)

### 第二层：收益是不是来自“统一”，而非换了更强组件

**建议主对照使用同一批组件，只改变它们共享什么状态、何时更新、更新怎样传到下一阶段。**

| 对照 | 做法 | 排除什么解释 |
| --- | --- | --- |
| 固定流水线 | 同样的记忆、搜索、排序模块，按固定顺序执行，反馈不联合改变各阶段 | 不是仅仅多放了几个模块 |
| 共享状态但固定编排 | 模块读同一份用户状态，但按固定时机更新、无联合调度 | 不是仅仅统一了存储 |
| 完整 Waterfall | 同一组件，使用拟提出的联合状态更新与调度规则 | 直接检验架构贡献 |
| 定点关闭 | 分别关闭画像更新、召回调整或排序调整，其余相同 | 哪个环节产生收益，哪个不可缺 |

“固定流水线”也应有合理预算与调参，不能故意写成弱版本。ClawRec 等外部系统另作有竞争力的整体对照；内部同组件对照更能解释 Waterfall 为什么有效。

若论文明确主张“召回与排序协同产生额外收益”，可再做一个很小的四格实验：保持画像模块相同，召回调整开/关 × 排序调整开/关，共四组，用同一最终有用率比较。完整组胜出说明联合使用有效；只有进一步比较“联合提升”与“两者单独提升之和”，才能谈额外协同，且要给不确定性，不能预设一定为正。

**KuaiRand-1K 放在这一层作真实行为补证。** 按时间先预测下一次已记录行为，再允许系统读到它，比较不更新、规则更新、Agent 更新；不要提前使用未来视频统计。它证明“理解历史和预测下一步更好”，并不证明“新策略已改善用户体验”。这套补测可以只覆盖反馈理解和画像更新，无须硬套跨网站搜索。

### 第三层：用户改变主意，整条链是否一起改对

**需要补建数据。** 现成材料缺少同一用户的自然语言纠正、临时目标到期、随后新推荐引发的反馈，以及旧候选/晚到搜索结果对新目标的干扰。

建议小而完整地覆盖四种场景：正常延续；明确纠正；临时目标及恢复；单次偶然点击。每段要保留原有长期偏好、变化发生时间、当前目标、可用内容与推荐后的反馈。

例子是拟构造场景，非真实用户结果：“平时看摄影；今天只想找两天的露营攻略；行程结束后恢复日常。”比较系统是否及时搜到攻略、把攻略排前、避免把一次出行写成永久兴趣，并在结束后恢复。再加一个只误点了一次露营内容的对照，检查是否过度调整。

两条可选证据路线：

- **受控真人实验：** 用户看到各自实际推荐后给反馈；采用随机分组或平衡顺序，记录推荐有用性与完成任务情况。证据更直接，规模先由试验波动决定。
- **合成多轮环境：** 模拟用户按“当前隐藏目标＋这次实际显示内容”生成反馈，固定初始条件和外部事件，对多种模拟设定重复。必须标成模拟结果，并用人工样本检查合理性；它不等于真人收益。

公平比较的是相同初始条件、外部目标变化、内容与预算。**系统推荐不同，之后的反馈应允许不同；不能既说在交互，又强迫所有系统收到原日志的同一条点击。**

## 3. 主指标用人话怎么说

以下是建议定义；数值均为解释用例。

| 看什么 | 最简指标与例子 |
| --- | --- |
| 整体有没有用 | **前 10 条有用率**：事先规定“有用”的评分门槛，10 条中 7 条有用就是 70%；重复项只算一次，缺项按无用处理。同预算比较。这同时受到召回与排序影响 |
| 好内容是否靠前 | **nDCG**：在只有 1 条相关内容的二值例子中，它在第 1 名得 1，在第 3 名约 0.5；各方法使用同一理想参照。SimBench 可保留 @20 作协议对齐 |
| 召回出了什么问题 | **已标注相关项的召回率**：已知 5 条相关，找到 3 条就是 60%。没有完整相关标注时，别声称这是全网召回率 |
| 改得够不够快 | **纠正后的无用曝光数**：用户明确改需求后，还刷到 2 条旧方向内容才稳定改好，比刷到 8 条更快；需预先规定何谓“改好” |
| 会不会改过头 | **到期后的恢复与误改率**：临时目标结束后的有用率；无明确变化的对照中，错误抛弃原偏好的比例 |
| 值不值得 | **成本与等待**：同一有用率要多少调用、多少 Token、等多久；同时报告平均与较慢请求的耗时 |

主表用最终推荐有用率和排序质量；变化场景用变化后整段的有用率、纠正延迟与恢复。画像文本的评分是解释性指标，不能替代用户最终看到的内容。按用户汇总并报告置信区间，避免把同一用户多轮记录当完全独立样本。

## 4. 不能把历史回放说成新策略闭环

原日志显示 A，用户点了；Waterfall 推荐 B，日志没有记录这次 B 的反馈。把 A 的点击奖励给 B，是错误的。随机曝光可以支持特定离线策略评估，但需满足曝光概率、可覆盖动作等条件；不能看到 KuaiRand 名字就直接成立。[经典离线评价论文](https://arxiv.org/abs/1003.5956)

KuaiRec 虽然有近乎完整的小矩阵，查到“用户曾看 B 的时长”也只是静态偏好近似。把它当新一轮反应，必须承认忽略了时间、顺序、疲劳和新目标。[KuaiRec 官方数据说明](https://kuairec.com/)

## 5. 复用 SimBench 评分脚本前的一个协议检查

2026-10-20 静态检查当前官方仓库发现：论文规定 nDCG 的理想排序来自各方法结果的共同评审池；公开 `aggregate_trajectory_judgments.py` 第 124–134 行却对当前一个返回列表自行排序得到理想值，第 254–260 行也只传入当前列表。按这段代码的公式，若 20 项全部为最低相关度 1，它们的 nDCG 仍会等于 1，无法表示这批内容整体很差。[论文 §4.1.2](https://arxiv.org/html/2607.23779v1)、[当前官方脚本](https://raw.githubusercontent.com/RUCAIBox/ClawRec/main/evaluation/trajectory/aggregate_trajectory_judgments.py)

这是**当前公开实现与论文所述协议之间的风险**。本次未运行复现，也未核对作者产生论文表格时使用的具体版本，不能据此断言论文数值错误。建议复用任务与数据前固定代码版本，落实共同评审池，并补绝对有用率；修改协议后应重跑各对照，不能直接拿新分数与论文表格比较。

## 最小落地范围

先做 SimBench 全链路与同组件编排对照，再做 KuaiRand-1K 反馈补测，最后补一组多轮变化实验。若核心主张特别依赖自然语言指令，可把 InstructRec 的一个领域加作指令诊断；MIND、BEIR、KuaiRec、KuaiSAR 不必全部加入。ACL 方向尤其应让“语言怎样改变共享状态和后续决策”可检验，仅把 LLM 当评分器不构成语言方法贡献。

未做：全量下载、文本覆盖实测、API 可用性测试、代码运行、论文复现或用户实验。主要风险：SimBench 是合成意图与离线隐藏目标，真实日志没有任意新策略的后续反馈；架构创新与收益均仍待上述对照证明。
