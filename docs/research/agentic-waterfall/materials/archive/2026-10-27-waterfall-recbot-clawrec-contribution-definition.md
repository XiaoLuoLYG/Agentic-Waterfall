# Waterfall 与 RecBot、ClawRec：逐项比较与主贡献候选 v0.4

> 历史材料：保留当时内容，不作为现行方案。当前以 [研究主方案](../../01-研究主方案.md) 和 [输入输出与数据流](../../02-输入输出与数据流.md) 为准。

2026-10-27。基于既有研究计划和定向一手核查；不重开广泛调研。本文定义研究候选，未实现、未评测。独立反证及官方代码定位见[核查报告](2026-10-27-waterfall-revision-mechanism-check.md)。v0.3是完整系统接口，v0.4是在这个系统中推荐主攻的具体修订机制；不代表现有产品已具有这些能力。

## 一页结论

**现有Waterfall设想与两篇工作高度相似，当前不能列出一个已经证实成立的原创方法点。推荐主攻：让系统能够改正自己从连续行为中学错的东西，并把修正真正落实到后续获取和推荐。**

普通人能理解的核心问题是：**用户后来说明“你之前理解错了”时，系统怎样改正那些由误解形成的认识，同时保留原本理解对的部分，让之后的内容跟着改对？**

“我之前想买，现在不想买了”和“那些浏览本来就是帮朋友查的”不同。前者是需求变化；后者说明某些行为从一开始就不应支持本人偏好。新列表都可能暂时换成相同内容，但系统以后记住什么、旧误解是否重新影响获取与推荐，会有所不同。

RecBot已有指令解析、局部冲突更新和按当前意图使用历史；ClawRec已有带证据的状态修订及完整搜推链路。所以主贡献不能只是“纠正画像”或“联合使用语言和行为”。本轮把候选写成三条规则：定位所纠正的解释；重新核算它支持的认识；复核受影响的获取和推荐决定。下面给出具体输入输出、反例和强对照。

**推荐贡献层级：**主方法是面向连续交互的理解修订；真实Waterfall-Loop数据与评测是补充贡献。边聊边看保留为完整使用情境。所有模型参数保持冻结，这里的“学习”仅指运行时理解与状态变化。

## 1. 三者的输入输出是否相同

| 系统 | 输入 | 主要中间结果与输出 |
|---|---|---|
| RecBot v2 | 当前信息流、用户原话、压缩偏好；规划器还用隐式历史和候选池 | 偏好约束、工具操作、候选分数和下一屏。 |
| ClawRec v1 | 新行为、明确上下文、旧状态与推荐反馈 | 统一事件、带证据的状态补丁、跨源计划及推荐列表。 |
| Waterfall v0.3 | 连续操作与内容上下文、原话、旧状态、候选和工具结果 | 状态修改、获取/重排/保持动作，再回读执行结果。其总体形式与近邻重合。 |
| Waterfall v0.4候选 | v0.3的同一输入，另明确记录此前如何解释行为、哪些判断依赖该解释 | 对理解的修订及其有效范围，重新核算相关状态的支持，再决定获取、重排或保持。该记录格式本身不算新颖性。 |

论文事实依据：[RecBot §§2–3.3](https://arxiv.org/html/2509.21317v2)、[ClawRec §§2.1–2.5](https://arxiv.org/html/2607.23779v1)。Waterfall两行均为提案说明。

## 2. 逐条比较：哪些不能再当主创新

| 比较项 | RecBot | ClawRec | 对Waterfall的判断 |
|---|---|---|---|
| 边浏览边用话控制推荐 | IRF直接研究此体验 | 接收明确上下文；不能因此称其已验证相同浏览界面 | 可作故事中心，不能据此宣称首创。 |
| 同时利用语言与行为 | 有 | 有 | 输入渠道组合已有。 |
| 把记录变成结构化决定 | 偏好与工具链 | 事件、状态补丁与计划 | 文本化、JSON、工具调用不能独立承担贡献。 |
| 局部更新并保留其他认识 | 有冲突处理 | 有证据状态修订 | 一句“只修改相关偏好”仍不足。 |
| 新语境改变历史的作用 | AIA按当前意图利用历史 | 明确上下文可纠正已有记录 | 必须进一步定义修改对象与支持关系。 |
| 跨来源获取与排序 | Searcher为扩展示例，核心评测围绕候选池 | 完整覆盖 | 多源能力能区别部分RecBot设置，不能区别ClawRec。 |
| 多轮反馈和继续调整 | 有模拟多轮及作者报告的线上验证 | 有反馈更新和跨事件状态 | 不能声称首次多轮，或把对手设成不再规划。 |
| 回溯解释修订的完整规则 | 所读定义未单列下述三条语义要求 | 通用patch可以容纳，未明确规定完整过程 | 是可检验的规格差异，尚不是已证明的独立能力差异。 |
| 真实连续交互数据 | 线上真实数据与离线模拟分开，不能概括成没有真人证据 | 主基准是合成轨迹；有人类质量验证 | 拟补可复用的真实曝光后交互与修订标注；尚未采集，不声称首次真人数据。 |

本表依据上述论文及[定向反证报告中的固定源码](2026-10-27-waterfall-revision-mechanism-check.md#clawrec-v1最强反证不只是一份静态画像)。所读版本未明示，不等于整个系统做不到。

还有一个必须纳入的边界：[A-MEM v11 §3.3](https://arxiv.org/html/2502.12110v11#S3.SS3)已经让新记忆更新旧记忆的上下文和属性。因此“后来知道更多，于是重新解释过去”本身也不能宣称原创。MARS的局部记忆维护、InterQuest的范围修订同样已有；本轮不另扩展一套通用记忆架构。

## 3. 本轮推荐的具体方法：三条规则

### 规则一：判断这次是在改需求，还是纠正之前的理解

读取新话语、当时可见的原始事件、旧解释及其依据。每项修改指出：回指哪些事件或内容、涉及什么目的/对象/受益人/任务范围，以及是当前目标变化、旧解释纠正、任务结束，还是证据不足。一句话可以包含多项修改，分别处理。

只出现“我现在想看徒步路线”，就更新当前目标；不能自行把过去的装备浏览解释成帮朋友。出现“前几天那些装备是替朋友选的”，才对有依据的历史片段修订归因。若回指不清，先执行明确的当前要求，保留未确定部分，不要求强行提问。

行为发生时间与这次获知解释的时间分别保留。修正会影响此后的判断，但不重写当时系统实际知道什么，也不给较早的评测前缀偷看后来解释。原始浏览记录不删除；与先前明确自述冲突时保留冲突依据，不把最新说法自动标成客观真相。

### 规则二：重算由该解释支持的认识，保留其他有效依据

每项任务或偏好判断要能回答：由哪些事件、在什么解释和范围下支持。旧解释被纠正后，停用不再成立的支持；根据其余依据决定保留、缩小、转为不确定或撤销。相关摘要也要重判，不能让已撤销的解释从旧摘要里重新进入决策。

例：装备浏览被解释为替朋友选购后，该片段不再支持“本人喜欢这类装备”。但若另有用户明确说过“我喜欢露营”，这条本人兴趣仍可保留。帮助朋友也是合法的当前任务；它可以继续影响本次内容获取，同时不变成本人长期偏好。停用支持也不等于新增一条“讨厌装备”。

该规则不要求图数据库，也不把支持简单按点击次数相加。结构能够表达独立依据和派生依据即可；语义判断仍可能出错，关系记录不会自动保证理解正确。

### 规则三：让获取和推荐使用修正后的理解

新的理解被接受后，重新判断依赖受影响认识的获取目的、查询约束和未展示候选。原理由失效时重新决定；无关决定和仍合适的内容可以保留。现有内容够用就重排，缺少所需内容才获取，没有影响就保持。

旧查询晚到的结果按当前有效理解重判，不能因为旧计划批准过就直接优先展示，也不能一律丢弃。已经展示过的内容保留为真实历史曝光。执行器应保证这些更新顺序一致；时序保护对强对照同样开放，不把修复一个缓存错误算作语言方法贡献。

**本方法的技术对象是“事件—解释—支持—决定”的关系及其修订规则。** 证据链接、局部补丁、重规划分别都已有，研究要验证上述具体关系是否带来独立价值。整体获取、排序、状态与反馈仍在；这里选出的是它们共同依赖的核心推理机制。

## 4. 一个能区别几种情况的完整例子

共同前缀：用户曾明确说喜欢日本建筑，最近又浏览一批东京酒店。系统对酒店浏览目的若没有明确证据，只能形成暂定解释。下面是设计案例，未运行模型，不预设近邻失败。

| 此刻用户说的话 | 应怎样理解过去 | 后续搜推应怎样变 |
|---|---|---|
| “之前是打算自己去东京，现在改去成都。” | 当时为本人查询仍成立；当前行程改变 | 当前找成都内容，保留真实过去，不自动抹去日本建筑兴趣。 |
| “东京酒店是帮同事查的，已经查完。我自己周末在成都，想找建筑散步路线。” | 修订酒店浏览的受益人；结束委托任务，建立当前路线任务 | 停用该片段对本人酒店偏好的支持；保留独立建筑兴趣，用于寻找成都路线。 |
| “我周末在成都，想找建筑散步路线。” | 没有足够回指，不补造过去的受益人 | 建立当前任务，过去不确定的归因仍不确定。 |
| “继续帮同事查东京酒店，但别把这些算成我的喜好。” | 委托任务继续；本人偏好与委托要求分开 | 仍可推荐东京酒店帮助当前任务，不把这些选择写成本人长期喜好。 |
| 用户没有发言，继续浏览 | 行为支持暂定理解；没有语言不等于没有反馈 | 可以继续适应，也可保持；单次点击不直接撤销仍有效的明确解释。 |

第二种情况下，原查询晚到的东京酒店通常不支持成都路线，但旧结果若包含仍有用的建筑材料，可按当前需要保留。随后用户结束成都任务，再浏览建筑，系统应依据仍有效的建筑兴趣继续，而不是从旧酒店片段重新推断本人要订东京酒店。

这个例子说明为什么只看“下一屏有没有成都”不够：几种系统都可能换对下一屏，却留下不同的长期状态。本轮不将任务结束或后续表现预先当作真实结果。

## 5. 主贡献及支持它所需的证据

**推荐的主方法贡献句：Waterfall提出一种面向连续交互的理解修订方法，将自然语言定位到具体行为解释及其支持关系，在保留有效知识的同时修正用户状态，并让后续获取和推荐一致响应。** 这是提案中的贡献表述，不含首创或性能结论。

**待检验主张：**同样的信息与工具下，这套规则比成熟组件的正常组合、完整日志重读更能改正误解且不误伤有效认识，并改善随后的内容有用性。状态正确而用户体验不变，只能支持较窄的状态修订结论；不能自动声称完整搜推收益。

**补充贡献：Waterfall-Loop真实连续交互数据及修订评测。** 在现有采集设计上增加需求变化/解释纠正/仅新增信息的区别、回指范围、独立支持与后续效果标签。首先记录真实使用中这些情形是否发生、频率和影响；不能全靠研究者安排的朋友选购脚本。受控辨别案例与自然交互分别标记，辅助模拟不能替代真人效果。

## 6. 足以反驳我们的强对照

| 对照 | 必须给予的能力 | 检验什么 |
|---|---|---|
| 连续运行的ClawRec适配版 | 保留完整状态修订、证据与重规划，看到同样原话和行为 | 近邻是否已自然完成这些修订。 |
| 成熟组件组合 | RecBot式局部更新和意图相关历史利用、证据状态与完整获取排序 | 现成部件正常组合是否已经足够。拿不到官方实现时标注style/adapted，披露改动。 |
| 完整日志重读的强Agent | 可看同一完整历史与最新纠正，重新建立状态、获取和重排；可保留来源、处理晚到结果 | 明确关系与增量修订是否比充分上下文下的通用理解更可靠。先在上下文放得下的条件比较。 |
| Waterfall v0.4 | 同模型、输入、工具及决策机会，采用三条修订规则 | 检验机制增益，不能依靠独享信息或更强工具。 |

机制分析只需两项替换：把回溯支持修订替换为合理局部更新；把受影响决定的重审替换为按最新状态全量重规划。后者允许正常刷新，不能靠对手继续使用过期计划制造优势。

主要结果仍看后续内容对当时需求是否有用；状态修订正确性、独立知识误伤和后续错误再现作必要诊断。U@40继续作为待校准默认值，任务完成后合理结束不能当失败。本轮不增加硬件或成本优化路线。

如果完整重读或成熟组合在有效状态和内容质量上已足够好，就没有依据宣称专门机制必要或更优。若只剩可解释性、实现可靠性或效率优势，按实际证据重新评估其是否足够重要，不自动换名为“统一架构创新”。

## 7. 本轮已经定下什么，接下来做什么

**保持确定：**完整搜推范围、边聊边看的使用情境、方法为主且真人数据为补充、冻结模型、保留A图、暂不实验。

**本轮新增：**推荐主攻“理解修订”，给出三条可执行规则、五种区别情形、四个强比较条件。没有将它写成已证实的原创方法；没有要求用户再选一堆分支。

**仍待证据：**与现成组合的独立增量、这些修订在真人使用中的频率和重要性、后续有用性收益。没有可信的录取概率；ACL相关性来自语言怎样修正行为含义及行动，不能只靠系统包含LLM。

**下一步顺序：**依据这份定义固定状态/解释/支持/动作的最小接口与Method伪代码，逐项静态核对上述案例；随后同步强对照与真人标注指南；之后才进入获准的实现、先导和正式实验。本轮完成的是比较和方法规格，不启动后续实验。
